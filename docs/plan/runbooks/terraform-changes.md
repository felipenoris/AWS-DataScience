# Runbook — Changing infrastructure by hand (Terraform, no CI/CD yet)

| | |
|---|---|
| **Scope** | Every by-hand change under `terraform-live/` and `terraform-modules/`, until Stage 8 hands this job to a pipeline |
| **Operator** | The **infrastructure user**, through `InfrastructureAccess` — one `awsds-infra-*` profile per account (§1) |
| **The one rule** | Modules are consumed **by git tag, from GitHub**. A module change and its callers are therefore **two commits, with the tags pushed in between** (§3) — in the wrong order, the commit hook blocks you with `invalid ref` |
| **First applied** | Stage 3 passes 1-2 (2026-08-16) — the [stage log](../../log/log-stage-03-networking.md) is the worked example |

## 0. The mental model, in five lines

- `terraform-modules/` holds reusable blueprints, versioned by git tags like `vpc-v0.1.0`.
  `terraform-live/` holds what is deployed: one folder per account, split into **slices** (`bootstrap/`,
  `foundation/`, …) that are applied independently.
- Each slice stores its **state** (Terraform's record of what it created) in that account's own S3
  bucket. Two untracked files point at it and feed it values — `backend.hcl` and
  `terraform.auto.tfvars` — both **generated by scripts, never edited**.
- `terraform plan` is read-only: it shows what *would* change. `terraform apply` does it. The
  `AWS_PROFILE` on the command line chooses the account — that is the wrong-account safety.
- Committing runs the pre-commit hooks. One of them (`terraform_validate`) runs `terraform init` on
  every changed slice, and init downloads the slice's modules **from GitHub by tag**. That is why the
  order in §3 exists.
- After every apply: re-plan and expect `No changes`, run the matching `aws/` instrument, update the
  docs the change touches (`docs/AWS_STATE.md` first), and write the stage log.

## 2. Recipe A — change inside a slice (no module touched)

1. **Branch** — never commit to `main` directly; the flow ends in a PR.
2. **Edit** the `.tf` files in `terraform-live/<account>/<slice>/`.
3. **Generate the two untracked files** (idempotent — safe to run every time):

   ```bash
   ./scripts/gen-backend-hcl.py <account> <slice> && ./scripts/gen-tfvars.py <account> <slice>
   ```

4. **Init** (needed once per fresh clone, and again whenever modules or backend change):

   ```bash
   AWS_PROFILE=<profile> terraform -chdir=terraform-live/<account>/<slice> init -backend-config=backend.hcl
   ```

5. **Plan to a file outside the repository, and read it** — the add/change/destroy counts, and that
   nothing is destroyed or changed that you did not intend. A `.tfplan` contains state (account ids
   included), which is why it must not live in the repo (`.gitignore` §saved-plans):

   ```bash
   AWS_PROFILE=<profile> terraform -chdir=terraform-live/<account>/<slice> plan -out="$HOME/tmp/change.tfplan"
   ```

6. **Apply exactly the file you read**:

   ```bash
   AWS_PROFILE=<profile> terraform -chdir=terraform-live/<account>/<slice> apply "$HOME/tmp/change.tfplan"
   ```

7. **Re-plan.** The only acceptable answer is `No changes` — anything else means the apply and the
   code disagree, and you stop and read.
8. **Verify and record**: `make check`; the matching instrument (`./aws/networking.py`,
   `./aws/egress.py`, …); the docs the change touches; the stage log entry.
9. **Commit, push, open the PR.** The hooks re-validate everything; no tag changed, so nothing blocks.

## 3. Recipe B — change a module (the two-commit order)

Why two commits: your callers pin `…//terraform-modules/<name>?ref=<name>-vX.Y.Z`, and the commit
hook's `terraform init` fetches that ref **from origin** — not from your working tree, not from local
tags. The ref must already exist on GitHub when the callers' commit runs.

1. **Edit** `terraform-modules/<name>/` and validate it alone:

   ```bash
   terraform -chdir=terraform-modules/<name> init -backend=false && terraform -chdir=terraform-modules/<name> validate
   ```

2. **Commit 1: the module change only.** Callers still pin the old tag, so nothing breaks and the
   hooks have nothing to fetch.
3. **Tag the new version** — one tag per command, semantic-version bump, **never reuse or move a tag**
   (a moved tag silently changes what every past and future init means):

   ```bash
   git tag <name>-v0.2.0
   ```

4. **Push the branch and the tags together**:

   ```bash
   git push -u origin <branch> --tags
   ```

5. **Commit 2: bump `?ref=` in every caller** (plus whatever caller edits the new version needs).
   The hook now resolves the new tag from origin and passes.
6. **Plan and apply each affected account** — Recipe A steps 4-9, re-running init (step 4) so the new
   module version is fetched.

## 4. Recipe C — a new slice

1. Create `terraform-live/<account>/<newslice>/` **and its row in `scripts/tfhygiene/layers.py` in the
   same commit** — a slice on disk with no row fails the hook, and the row is what `make down` reads
   (an unregistered `[E]` slice is a bill nobody is told about).
2. A new *kind* of slice (a name not in `layers.py` `RANKS`) declares its dependency rank there first.
3. Then Recipe A from step 3. The state bucket already exists (`bootstrap/` made it), so the first
   init just works.

## 5. Cross-account changes

When one change spans accounts, the arrows decide the apply order: a **requester before its
accepter**, an **authorization before its association**, and any **route only after the peering is
active**. The pattern that satisfies all three in the fewest applies is: minimal requesters in the
originating accounts, then everything else as **one ordered apply on the accepting side**, reading the
peers' facts through aliased providers instead of pasting ids.
`terraform-live/production/foundation/peers.tf` is the worked example, comments included.

## 6. When the commit is blocked

| Symptom | Cause | Fix |
|---|---|---|
| `invalid ref: "<name>-vX.Y.Z"` | The tag is not on origin | Push the tags. If this is a module+caller change, you skipped §3's order: unstage the callers, commit the module, tag, push, then commit the callers |
| Module fetch asks for SSH keys / hangs | Init fetches over **your** git credentials | Fix your SSH agent — this is git auth, not Terraform and not AWS |
| Stale module or provider errors after a tag bump | Old `.terraform/` cache | `rm -rf terraform-live/<account>/<slice>/.terraform`, re-run init |
| `checkov` FAILED | A real finding, or a deliberate exception | Fix it — or suppress with `# checkov:skip=CKV_xxx:reason` written **inside** the resource block, first lines. Above the block it is **silently ignored** |
| `terraform_fmt` modified files | Formatting | `git add` the reformatted files and commit again |
| A hook seems to want AWS credentials | It must not — validate runs `-backend=false` | Read the error again: it is almost always the module fetch over SSH, never AWS |

## 7. What you never do

- **Apply a plan you did not just read.** A stale plan fails on its own (the state serial moved), but
  the rule is about you, not Terraform.
- **Edit `backend.hcl` or `terraform.auto.tfvars`.** Regenerate them (§2 step 3) — they carry a
  header saying exactly this.
- **Force-add anything `.gitignore` refuses** — state, plans, tfvars all carry account ids.
- **`terraform apply` under the wrong profile.** The state bucket rejects it (that is the guard), but
  read the profile before running, not after failing.
- **`-target`, or improvised `state rm` / `state mv` / `import`.** Each is a session of its own with a
  plan written first, never a quick fix.
- **Hand-apply an `[E]` or `[D]` slice.** Their lifecycle belongs to `make up ENV=<account>` /
  `make down ENV=<account>` (D11) — this runbook covers the `[P]` slices those targets refuse to
  touch.
- **Retag** (`git tag -f`). Version forward instead: a new tag costs nothing; a moved one corrupts
  the meaning of every init that ever resolved it.
