# D28 — The production workflow contract: what must exist for a scientist-authored workflow to deploy

**Status:** Decided (2026-08-08): Production runs workflows headless — no domain, no portal, no blueprint ever touches a deployment target. The pipeline creates, from the application repository, exactly six artifact classes.

**Amended 2026-10-13:** classes (2b) and (2c) join the six, both code a task reads from S3 rather than from an image, and the decision states what starts code in a deployment target (below).

**Amended 2026-10-15 ([D41](D41-sagemaker-application.md)):** class (4) gains a chain's state machine and
schedule, class (4b), and the CI/CD CLI deploys the application between the Sandbox projects and makes
the bundle; the pipeline stays the deployer here. The image carries the dependencies alone and a
processing task's code joins as class (2d) (D41 item 7), and the execution role writes its application's
result and inbox prefixes (D41 item 10).

**In one line:** What crosses the gate into a headless deployment target: a closed list of artifact classes, carried by the repository; a workflow starts whatever runs there.

## Rationale and consequences

D26 forces the question: the workflow is authored in a project of the unified domain, in Sandbox, Production has no domain (D17), so what crosses the gate? **The project's git repository is the promotion vehicle**, and the deployable set is: **(1)** the container image in Production ECR (D14), which since D41 carries the dependencies alone, built from the lock; **(2)** the **workflow definition** — MWAA Serverless YAML — versioned in the repo, deployed by the pipeline to a versioned S3 prefix in Production; **(3)** a **per-workflow IAM execution role** built from `terraform-modules/iam-role`, which starts and observes the workflow's jobs and holds no lake permission, the LF producer grants (D22/D25) being the job role's (Stage 10 step 1.3), its S3 reaching only the result and inbox prefixes its application's S3 operator tasks write (D41 item 10) — one role per workflow is the Serverless isolation model, and the least-privilege property a provisioned MWAA environment structurally cannot offer; **(4)** the orchestration resource itself: **`awscc_mwaaserverless_workflow`** (D7 alternative A), and **(4b)**, since D41, for a workflow in a chain, the chain's **`aws_sfn_state_machine` + `aws_scheduler_schedule`** (alternative B as the layer above), created by the pipeline with the workflow, which then carries `TriggerMode` `manual_only`; **(5)** an explicit **`aws_cloudwatch_log_group` per workflow** — named, retention set — wired into A's `LoggingConfiguration`, and one per account for the chains' state machines under `/aws/vendedlogs/states/`, so execution logs are a deliverable rather than an accumulation of default log groups nobody expires; **(6)** for ML, the **model package group** (`aws_sagemaker_model_package_group`, Stage 9) whose resource policy lets the pipeline register and approve versions, Staging read approved ones, and the Sandbox readers read status only (INT-07, which absorbed INT-04 at 6b). **Terraform support for (4) verified 2026-08-08:** `AWS::MWAAServerless::Workflow` exists in CloudFormation and the `awscc` provider exposes it as `awscc_mwaaserverless_workflow` — re-verify at Stage 10; fallbacks in order: `aws_cloudformation_stack` wrapping the CFN type, then the `CreateWorkflow` call from the release job, the CI/CD CLI's form (Stage 10 step 4; design B left the ladder with D41). Provisioned MWAA (`aws_mwaa_environment`) is not a rung: D7's amendment of 2026-09-05 removed it, and Stage 10 step 4.3 denies `airflow:CreateEnvironment` on the root SCP. **What authoring must respect, enforced by a promotion lint in Stage 8's CI:** the workflow YAML references the container by ECR URI and digest, never by anything project-scoped, and no operator may reference a domain resource (project connections, portal-scoped IDs). A workflow that only runs where the portal exists is not a promotable artifact. The lint runs on the copy the pipeline renders per environment: the repository's YAML carries the CI/CD CLI's variables, which the CLI resolves per project (D41). INT-12, INT-13 and INT-14 carry the integration proofs.

**The classes added 2026-10-13.** **(2b)** the workflow's operator code package: the `Code` object a `PythonOperator` or `BashOperator` task runs on the worker, which the service copies at each save and versions with the definition, so it is pinned by its S3 `VersionId` like (2); Stage 8 step 5.6 builds and checks it, as 6d step 4.5 asked. **(2c)** a Glue job's script and every file its arguments name (`--extra-py-files`, a wheel in `--additional-python-modules`): Glue reads them from S3 when each run starts and takes no version, so no pin holds them and a job runs whatever the key holds then. The job is declared by the application's Terraform and names a script under the release's own prefix; how that prefix is kept from changing, against roles that can write its bucket, is Stage 10 decision 12. A Visual ETL flow reaches a deployment target only as (2c): its `.vetl` and its portal schedule stay in the project, and the script its editor generates is what graduates.

**The class added 2026-10-15.** **(2d)** a processing task's code: the application's `src/`, which the job reads as its code input on the application image (1) that carries its dependencies (D41 item 7, Stage 10 decision 7). A `ProcessingInput` names a prefix the job reads at each run and takes no version, so (2d) lies under the release's own prefix with (2c), written once by the release job, kept from change by Stage 10 decision 12's statement and checked against the release's manifest by the lint's rule (h) of Stage 8 step 5.6.

**What starts code in a deployment target.** Nothing runs code by hand in Staging or Production (D17), so whatever must run there is started by a workflow. The workflow is the activation, and the code its tasks start is the content: the Python project, run as a SageMaker job on the application image (1) with its code as the job's input (2d); orchestration code on the worker (2b), never a data path; a Glue script (2c) for a step that reads or writes governed data, since Lake Formation vends to Glue and never to a SageMaker job (Stage 9 step 3.1). A data scientist therefore promotes a notebook's logic as code plus the task that calls it, and a workflow may hold a single task; the notebook itself does not graduate (6d decision due 14). Structure is applied rather than started: a governed schema's DDL runs in the pipeline at deploy time (Stage 9 step 9.4), a governed table and its LF-Tags are declared in Terraform before the first write (Stage 9 step 2.1), and the jobs a workflow starts are declared in the application's slice. A model follows the rule by another path: its training code runs in a workflow in Production, and the pipeline registers the version a person approves (Stage 10 step 5). The SageMaker Unified Studio CI/CD CLI draws the same line, separating a manifest's content from its activation, which is a workflow or tests; it deploys the application from its repository into the `dev` and `test` projects and makes the bundle, and the pipeline deploys the bundle here (D41).
