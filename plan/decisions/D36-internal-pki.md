# D36 — Custody of the internal PKI

**Status:** Decided (2026-08-09): **its own `[P]` slice, `production/pki/`, with its own state and its own
KMS key; no revocation path, and the compensating controls are detective**

**In one line:** The internal CA root gets a slice, a state file and a KMS key of its own — so "who can mint
a certificate for any internal name" is an isolable question rather than a subset of "who administers the
VPC" — and because it cannot be revoked, what watches it is written down here rather than assumed.

**Related decisions:** [D15](D15-tls-internal.md) (which created the CA),
[D16](D16-break-glass.md) (the other credential IAM cannot revoke), [D3](D03-terraform-state.md),
[D31](D31-approver-read.md) (the same key-policy-as-control shape)

## Why this is a decision and not a note inside D15

D15 chose an internal CA. It did not settle who holds the key, and the answer is not a detail: **the CA root
is the second credential in this design that IAM cannot revoke.** The first is the Management account root,
and [D16](D16-break-glass.md) exists as a decision for exactly that reason — a credential that cannot be
scoped needs its compensating controls written down instead of implied. The same test applied here produces
a worse result than D16's in one specific way, and a better one in another:

- **Worse: there is no revocation path at all.** This design has no CRL and no OCSP responder — a leaf
  certificate cannot be revoked, and a compromised root is repaired only by generating a new one and
  **redistributing trust to all three client surfaces** (INT-19): the laptop, the `dev-env` image and the
  runners. No IAM action does anything about it. D16's root can at least have its password rotated in one
  place.
- **Better: it is not a sign-in credential.** Holding it grants no API access, no console, no account. Its
  entire power is impersonating an internal endpoint to a client that trusts the root — which requires being
  on the path as well, inside the VPN or the VPC.

And there is an asymmetry that D16 does not have, which is what actually forces the choice below.
**This root is generated by Terraform and lands in a state file.** That converts "who can read that state
bucket" into "who can issue a certificate for any internal name, offline, with no API call in anyone's
CloudTrail". Lesson 18 is the reason to state it plainly rather than treat it as covered: the infrastructure
user authors the state bucket's own key policy, so it is not constrained by it. **The point of this decision
is not to prevent that — it cannot be prevented — but to keep the reach from being acquired accidentally, by
anyone who merely needed to change a subnet.**

## The decision

1. **A slice of its own: `production/pki/`, layer `[P]`.** Not `production/foundation/`, where D15's first
   draft put it. Foundation is the networking slice: it is opened to change a CIDR, add a route, accept a
   peering. Every one of those edits would otherwise be made by a principal holding the CA, and every
   `terraform plan` against it would decrypt the root. Separating them costs one folder and one backend
   block.
2. **Its own state file and its own KMS key.** The key is the control, not the folder — a separate slice
   sharing Production's general key would put the root back inside the blast radius it was moved out of.
   This is the same shape D31 uses for the derived zone: *the key policy is what says who may read this*.
   Cost: ~USD 1/month, in `plan/cost-model.md`'s KMS row.
3. **Created early — applied before Stage 6, alongside Stage 7 step 5.** Not a placement question but a
   scheduling one: the `dev-env` image exists from Stage 6 (INT-01) and has to be built with the root
   already in it. A CA created at its natural place in Stage 7 would mean the first image is built without
   it and rebuilt afterwards. Stage 7's ordering note already pulls step 5 forward for the same class of
   reason; `pki/` joins it.
4. **Leaves are issued from this slice and imported into ACM by the consuming slice.** `production/egress/`
   (or `tooling/`, if Stage 7 chooses nginx-on-instance) reads the certificate through
   `terraform_remote_state` outputs. **The root's private key is never an output** — only the CA
   certificate and the issued leaves are.
5. **What watches it, since nothing prevents it.** All three are detective, in the D16 tradition:
   - CloudTrail **S3 data events** on the `pki/` state prefix — a read of that object outside a planned
     change is the signal. This is the one that has to be enabled deliberately: management events would not
     record it. Stage 11 turns data events on; this prefix is a reason to include it in the scope rather
     than an afterthought.
   - A CloudWatch alarm on `kms:Decrypt` against the PKI key by any principal other than the infrastructure
     role, and on any `kms:ScheduleKeyDeletion` for it.
   - The CA certificate's fingerprint recorded in `log/stage-07-gitlab-runners-ecr.md` when it is created,
     so "is the root my clients
     trust the root I generated?" is answerable at all. Without it, a substituted root is indistinguishable
     from the real one by inspection.
6. **Rotation is a rebuild, and it is rehearsed once.** Generating a new root means rebuilding the `dev-env`
   image, re-running the runner user data and re-importing on the laptop. Do it once, deliberately, at
   Stage 12, and record the measured time — the same discipline Stage 7 applies to the GitLab
   backup/restore cycle. A recovery path that has never been walked is a claim, not a path (Lesson 5).

## Naming, settled here so it is not reopened per account

Internal zones are `<account-role>.internal` — `prod.internal`, `sandbox.internal`, `development.internal`
— plus `pages.internal`, which is a separate **domain** rather than a separate host because GitLab Pages
serves user-supplied content (Stage 7 step 4). **`.internal` is the right choice and is now permanent:**
ICANN reserved the string from delegation in the root zone in resolution 2024.07.29.06, precisely for
private use, so it cannot collide with a future gTLD. `.corp` and `.home` were once applied for; `.local`
collides with mDNS.

Route 53 **private hosted zones do not delegate to each other**, so a single parent zone would not save the
per-account associations — the per-account zone is not a style choice, it is the only shape that works.

## Consequences

- **Per business unit (D35), the cost of a new Sandbox now includes two PKI items**, not one: the Route 53
  associations *and* the CA root reaching that unit's `dev-env`. Both belong to
  `terraform-modules/sandbox-unit/` (Stage 14 step 1), or they become Lesson 14 — a thing that must appear
  in N places by hand and will be missing from one.
- **`production/pki/` is `[P]` and must be excluded from every `make down` path**, like the other trust
  anchors. Rotating a root on a session boundary would invalidate three client surfaces at 09:00.
- **The ALB-versus-nginx choice in Stage 7 does not reach this decision.** Both consume the same leaves from
  the same slice; only the attachment point differs.

## Revision trigger

Re-open if a fourth client surface appears that cannot take a custom root (INT-19's fallback (ii) fires
twice), if AWS Private CA's short-lived mode falls inside the D12 ceiling — it brings a real revocation path
with it — or if D15 phase 2 at Stage 13 retires the internal CA in favour of public certificates, in which
case this decision is superseded rather than revised.
