# D31 — What a release approver may read

**Status:** Decided (2026-08-08): **a bespoke `DeploymentManagerAccess` replaces `ReadOnlyAccess`, and the derived zone gets its own CMK whose key policy is the structural control**

**In one line:** A bespoke `DeploymentManagerAccess` replaces `ReadOnlyAccess`, and the derived zone gets its own CMK.

**Related decisions:** [D18](D18-data-scientist-access.md), [D19](D19-derived-zone.md)

**Referenced by stages:** [Stage 1b](../stages/stage-01b-identity-and-controls.md), [Stage 5](../stages/stage-05-data-foundation.md)

## Rationale and consequences

`ORGANIZATION.md` splits the approver persona in two and justifies the split *entirely* with an argument about what an approver may read — "an approver who can already read everything is not exercising a control". It then applied that argument to one of the two approvers: the governance manager got a permission set whose denials are its point, and the deployment manager got the AWS-managed `ReadOnlyAccess` on the lifecycle accounts. The argument is symmetric; the plan was not. **The picture is better than "reads everything", and the precision is what shaped the fix.** `ReadOnlyAccess` has no `athena:StartQueryExecution`, so this persona cannot *originate* a read of the lake — no query, no Lake Formation path. It also has no `kms:Decrypt`, so against SSE-KMS buckets a `GetObject` fails. What it does reach: anything unencrypted or SSE-S3, `logs:GetLogEvents` over log *contents*, and — the concrete path — **`athena:GetQueryResults`, which reads other people's query results**. So the exposure was real but narrow, and it was being prevented by encryption rather than by design, which is the kind of accident that stops being true the first time someone creates a bucket without a CMK. **Two changes, and the second is the one that outlives the first.** *(1) `DeploymentManagerAccess`*, built in the shape D18 already uses for `DataScientistProdAccess` rather than reaching for a managed policy: CloudWatch Logs read (including Logs Insights, because diagnosing a failed promotion is the job), SageMaker job/pipeline/Model Registry **status**, Glue catalog metadata, ECR image metadata and scan findings, Step Functions and Scheduler execution status, and `s3:GetObject` on **enumerated** prefixes only — build artifacts and test reports. Denied explicitly rather than by omission: `athena:*` (both the query and the results), `kms:Decrypt`, `secretsmanager:GetSecretValue`, `ssm:GetParameter*`, Terraform state buckets, and the whole control plane. Note what this persona does *not* lose: the release approval itself lives in GitLab and consumes no AWS permission at all (Stage 1b step 3), so narrowing the AWS side costs the approval nothing. *(2) The derived zone gets its own KMS CMK* in each Interactive account, separate from the account's general-purpose key, and **the key policy is where "who may read materialised restricted data" is expressed** — granted to the project execution roles and the `DataScientistAccess` set, to nobody else. This is default-deny and survives forgetfulness: a new derived prefix under the same key is covered without anyone updating a list, which a prefix deny-list is not. **It closes a D19 gap that has nothing to do with this persona:** D19 lists five practices for the derived zone — per-principal prefixes, lifecycle expiry, scoped `PutObject`, Macie scope, classification inheritance — and none of them is about the key, even though the key is the natural place to say who may read the copy. **Cost:** two more CMKs, ~USD 2/month, added to the KMS row in `plan/cost-model.md`. **The zero-cost variant, recorded rather than chosen:** S3 sets the KMS encryption context to the object ARN, so a single account key can carry a `kms:EncryptionContext:aws:s3:arn` condition scoped to the derived prefix instead of a second key. Subtler and more fragile; take it only if the two dollars ever matter. **Why this was worth doing at one operator, where the persona is the same human as every other:** `plan/institutional-delta.md` says what this lab produces is the *pattern*. A sloppy permission set on a control principal teaches the sloppy pattern, and the plan wrote three bespoke sets for the data scientist (D18) precisely to avoid that. This was the one place it reached for a broad managed policy, and it was for an approver.
