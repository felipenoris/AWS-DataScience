# D30 — The SCP recovery principal — a named role exempt from every custom deny

**Status:** Decided (2026-08-08): **build it. One role, `awsds-scp-recovery`, in every SCP-governed account, excluded by an explicit `ArnNotEquals` condition from every `Deny` statement this project writes**

**In one line:** `awsds-scp-recovery`, one enumerated role exempt from every custom `Deny`; adopted against the recommendation, with the trade-off recorded.

**Related decisions:** [D10](D10-identity-center-delegation.md), [D16](D16-break-glass.md), [D27](D27-catalog-maintenance.md)

## Rationale and consequences

Raised as "option E" alongside D16 and initially recommended *against*, because with root as the break-glass credential the recovery path already exists without a hole: SCPs never apply to the Management account, so a bad policy can always be detached from there. **The user chose to build it anyway, and the trade-off is recorded here rather than argued: this project gains a principal that is permanently outside every guardrail it writes.** The two reasons that make it defensible are worth stating, because neither is "we need it to recover": (i) fixing a policy *in place* keeps the repair out of the Management console, which principle 1 wants touched as little as possible; (ii) the carve-out condition is a real production pattern with real sharp edges, and building it is the kind of thing `plan/institutional-delta.md` says this lab exists to learn — learning the pattern is a first-class goal here, not a consolation. **The two sharp edges, which are the whole engineering of this decision.** *First, the account-ID wildcard is a hole, not a convenience.* Writing `arn:aws:iam::*:role/awsds-scp-recovery` exempts a role of that name in **any** account — so anyone who can create a role in any account of the organization can name their way out of every deny. The condition therefore uses **`ArnNotEquals` with an explicit, enumerated list of role ARNs**, one per account, and no wildcard anywhere; and the same SCP set carries a companion deny on `iam:CreateRole`, `iam:PutRolePolicy`, `iam:AttachRolePolicy` and `iam:UpdateAssumeRolePolicy` for that role name, so the exemption cannot be minted or widened from inside a governed account. *Second, the condition has to be in every deny statement or it is worse than useless* — a set where some policies carry it and others do not is a set nobody can reason about, and the drift is silent. So the condition is **generated, never typed**: see the consequence below. **What the role is.** Least privilege still applies, because an SCP exemption removes a *ceiling* and grants nothing: the role's own identity policy is scoped to the actions the SCPs deny, which is a knowable list since the same code writes both. It carries a permissions boundary (`plan/conventions.md` §6), a 1-hour maximum session, a trust policy admitting only the infrastructure user's Identity Center role **and requiring `aws:MultiFactorAuthPresent`**, and a CloudTrail alarm on every `sts:AssumeRole` into it — the same shape as the root alarm in D16, and for the same reason: a credential that is never used in normal operation should be loud the one time it is. Layer `[P]`, created in each account's `foundation/` slice. **The consequence this forces, and it closes a hole that predates it: the SCPs have to live in code.** Until now no stage owned them after Stage 1b created them by hand, and nothing imported them — so "generated, never typed" was not even possible. Organizations supports a **delegated administrator for policy management**, so they move into `terraform-live/identity/` alongside the permission sets (D10), applied with the delegated-admin profile and never with credentials in Management. Stage 2 step 5 imports them with the rest. A CI check rejects any `Deny` statement in that slice lacking the carve-out condition, in the same spirit as the region-literal grep of Stage 2 step 9. **What this is not.** It is not the per-function carve-outs the plan already has and keeps — the catalog-maintenance role exempt from the `Data` OU's Glue deny (D27), or a deploy role exempt from a specific deny so automation does not stall. Those exempt one principal from *one* deny because that is the principal's job. This exempts one principal from *all* of them because of what might go wrong, which is a different thing and carries a different risk. **Revision trigger:** the first time a second person has access to this organization, or the first time the role is assumed for anything other than repairing a policy. At that point the institutional answer in `plan/institutional-delta.md` — no standing exemption, time-boxed elevation per incident — stops being theoretical.
