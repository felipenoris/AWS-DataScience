# D16 — Break-glass access

**Status:** Decided (2026-08-07), credential settled (2026-08-08): **the Management account root user, and nothing else**

**In one line:** Break-glass is the Management account root and nothing else; every compensating control is detective.

## Rationale and consequences

"No IAM Users" (principle 2) has no answer for an IAM Identity Center outage or a misapplied SCP that locks everyone out, and an absolute rule with no escape hatch is one that gets broken improvised, under pressure, at the worst moment. **The credential is the Management account root**, which turns out to remove the exception rather than document one: the root is not an IAM user — it exists whether or not you want it — so principle 2 no longer needs the words "with exactly one exception". There is nothing to create, nothing to rotate beyond password and MFA, no permissions to design and nothing for Terraform to manage. It also merges two things Stage 1a was describing separately without noticing: securing the root (step 1) and building the break-glass path (step 5) are the same credential. And it composes with centralized root access management (1a step 6), which strips root credentials from the **member** accounts and does not touch Management: every member root disappears, one root remains, and it is the break-glass. **The honest cost: the root cannot be scoped.** An IAM break-glass user could have carried a two-line policy — `organizations:DetachPolicy` and `DisablePolicyType` — and nothing else; the root can do everything, including closing accounts and changing billing. Every compensating control is therefore detective and procedural: MFA enabled, password stored offline (never in this repository, never in `secrets/`), never used in normal operation, and a CloudWatch alarm on any use. **`iam:CreateAccessKey` on the root becomes an invariant rather than hygiene** — an access key there would be a permanent, unscoped, SCP-immune credential sitting in a file — and since SCPs cannot constrain the Management account, the instrument is detection: the AWS Config rule `iam-root-access-key-check`, enabled with the recorder scope in Stage 1d step 10. **The alarm must not notify the mailbox that is the login.** Root sign-in is e-mail plus password, and the e-mail is the one in `secrets/emails.md`; if the SNS subscription points at the same address, whoever holds the mailbox holds the credential and the alarm together. **MFA: enabled, type deliberately not specified.** The user already has MFA on this root, and nothing in this plan depends on which kind — the alarm does not, the SCP exemption does not, the procedure does not. This is recorded as a decision rather than left silent so that a later reader does not "fix" it back to a hardware requirement, which is what an earlier version of this row said and which contradicted Stage 1a step 1 in the same breath. What *does* still matter, and is not about the type: **if only one MFA device is registered**, losing it means AWS account recovery, which depends on the phone number and payment method on the account — so those are part of the design and must be current. **This is the only recovery path, and it covers all three failures** — Identity Center is down, the organization itself is broken, or a custom SCP denies something it should not. A second, narrower path was adopted and then reverted (D30), so no principal inside a governed account can work around a bad deny. The consequence is that the cheap defence moves *upstream*: every candidate policy is exercised against the `Policy Canary` before it is attached to anything real (D29), and the detach command is written down with the Management console already open before the first attach (Stage 1c step 7). Documented in Stage 1a and tested once, before any policy exists.
